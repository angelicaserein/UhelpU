# UhelpU 游戏功能与机制总览

## 1. 文档目的

这份文档基于当前仓库的目录结构、核心源码、已有技术文档、页面脚本、关卡脚本和辅助页面整理而成，目标是把这个游戏目前已经涉及到的功能、机制和外围支撑系统集中说明清楚。

这份文档的写法是“按功能归类”，不是逐个文件做流水账。这样更适合后续开发、交接和查阅。

---

## 2. 项目总体定位

UhelpU 是一个基于 p5.js 的 2D 平台解谜游戏。项目主体围绕以下几个核心体验展开：

- 平台跳跃与基础操作
- 录制与回放分身协作
- 按钮、平台、地刺、传送门等机关联动
- 房间切换、检查点与传送点
- 多模式关卡流程
- 排行榜、账号、成就、教学、计时等外围体验系统

项目入口为 `index.html + main.js`，使用 p5 实例模式运行，资源加载后由 `AppCoordinator` 协调页面系统和关卡系统。

---

## 3. 运行入口与主循环

### 3.1 启动流程

正式游戏页入口是 `index.html`。

启动顺序如下：

1. 加载 `p5.js` 与 `p5.sound`
2. 执行 `main.js`
3. 初始化 Firebase REST 接口封装
4. 预加载资源 `Assets.loadAll(p)`
5. 创建 `AppCoordinator`
6. 初始化页面切换器、事件总线、关卡管理器
7. 显示主菜单

### 3.2 运行时总协调器

`js/AppCoordinator.js` 负责统筹整个游戏运行流程，主要职责有：

- 创建 `EventBus`
- 创建页面切换系统 `SwitcherMain`
- 创建关卡管理系统 `LevelManager`
- 监听关卡加载、卸载、暂停、结算、返回选关等事件
- 负责通关失败结果页与胜利页的切换
- 负责按关卡切换背景音乐
- 在主循环中推进页面渲染和关卡更新

### 3.3 主循环职责划分

每帧由 `AppCoordinator.updateFrame()` 推进：

1. 处理待执行的重载请求
2. 更新当前活动页面
3. 绘制当前活动页面
4. 更新关卡逻辑
5. 处理死亡重载
6. 如果有 Overlay，则最后绘制浮层页面

这意味着项目使用的是“页面系统 + 关卡系统并行存在，最后用浮层覆盖”的结构。

## 4. 页面系统与用户流程

### 4.1 页面切换架构

页面系统由以下几层组成：

- `SwitcherMain`：总切换器
- `SwitcherStaticPage`：静态页面切换器
- `SwitcherGamePage`：游戏页面切换器
- `PageBase`：页面基类
- `GamePageBase`：游戏页基类

其中：

- 静态页面负责主菜单、语言选择、身份输入、世界选择、关卡选择、成就页、排行榜、故事页等
- 游戏页面负责具体关卡内的 UI 与暂停/提示/设置窗口
- Overlay 用于失败页、暂停窗、结果窗等覆盖在游戏画面上层的内容

### 4.2 页面基础能力

`PageBase` 提供的通用机制包括：

- 页面进入和退出生命周期
- DOM 元素注册与自动清理
- 页面级键盘导航注册
- 语言切换监听

### 4.3 游戏页基础能力

`GamePageBase` 提供的能力包括：

- 返回关卡选择按钮
- 暂停按钮
- ESC 暂停处理
- 暂停窗口、设置窗口、Hint 窗口
- 计时 UI
- 场景提示板与 HintButton 联动
- 关卡计时快照保存与恢复

### 4.4 用户完整页面流程

当前项目的典型用户流程是：

1. 主菜单
2. 语言选择页
3. 身份输入页
4. 世界选择页
5. 模式选关页
6. 进入关卡
7. 关卡中暂停、查看提示、设置按键或音量
8. 失败进入结果页，胜利进入结算页
9. 可返回继续挑战或切换模式

### 4.5 主要静态页面

当前静态页面大致包括：

- 主菜单页
- 语言选择页
- 名字输入页

- 游客模式进入

## 5. 事件总线与状态驱动

项目通过 `EventBus + EventTypes` 在系统之间解耦。当前主要事件包括：

- `LOAD_LEVEL`
- `UNLOAD_LEVEL`
- `RETURN_LEVEL_CHOICE`
- `AUTO_RESULT`
- `PAUSE_GAME`
- `RESUME_GAME`
- `SIGNBOARD_INTERACTED`
- `SIGNBOARD_OUT_OF_RANGE`
- `TUTORIAL_START_REQUESTED`
- `TUTORIAL_CLOSE_SIGNBOARD`
- `NPC_DIALOGUE_START`
- `NPC_DIALOGUE_NEXT`
- `NPC_DIALOGUE_END`

这些事件把页面系统、关卡系统、教程系统、公告牌系统和结算系统串联起来。

## 6. 关卡系统总体结构

### 6.1 关卡基础类

`js/level-design/BaseLevel.js` 是标准关卡基类，负责：

- 维护实体集合 `entities`
- 初始化 RecordSystem、PhysicsSystem、CollisionSystem
- 创建和销毁 Replayer
- 清空关卡资源与事件监听
- 更新物理
- 更新碰撞
- 按 zIndex 绘制实体
- 绘制录制 UI

### 6.2 关卡管理器

`LevelManager` 负责：

- 维护所有关卡类的映射表
- 根据 `levelIndex` 加载不同模式与编号的关卡
- 卸载关卡
- 维护当前关卡索引
- 关卡标题叠层展示
- 摄像机轻微前倾效果 `cameraNudge`
- 检查点恢复
- 传送点注册
- 死亡后的延迟重载
- Portal 过渡效果管理

### 6.3 房间与关卡组织方式

项目中的关卡除了单屏布局，还支持房间制结构：

- `Room.js` 用于定义房间
- 每个房间可配置自身实体
- 每个房间可配置上下左右出口
- 玩家触边可触发房间切换

因此游戏支持“单关卡多房间”的设计，而不是只支持一张固定画面。

### 6.4 模式与关卡分组

关卡按照目录分为五套：

- `js/level-design/demo1/`
- `js/level-design/demo2/`
- `js/level-design/easy/`
- `js/level-design/hard/`
- `js/level-design/special/`

每套均包含 `Level1` 到 `Level10`，属于不同模式下的十关结构。

## 7. 核心玩法系统

### 7.1 角色控制系统

`js/character-control-system/` 提供完整的输入到动作链路，包含：

- `ControllerManager`
- `ControlComponent`
- `ControlMode`
- `EventProcesser`
- `IntentResolver`
- `ActionValidator`
- `PhysicsApplier`

这套系统的职责是：

- 接收键盘输入
- 把按键转换为意图
- 验证当前动作是否允许执行
- 把意图写入角色运动状态
- 支持玩家与 Replayer 使用不同控制模式

### 7.2 物理系统

`js/physics-system/PhysicsSystem.js` 负责：

- 速度、加速度、位置积分
- 角色落地状态维护
- 跳跃冷却
- coyote time 容错跳跃
- 水平支撑链速度传播
- replayer 离开支撑面后的短缓冲

当前物理结构不是简单只改坐标，而是把“站立支撑关系”和“水平位移传播”纳入系统设计。

### 7.3 碰撞系统

`js/collision-system/` 提供完整的碰撞处理链：

- `CollisionSystem`
- `detectorMap`
- `resolverMap`
- `responderMap`
- `CollideComponent`
- `enumerator`

碰撞系统支持的核心能力包括：

- 动态体、静态体、触发器分层处理
- 矩形碰撞检测
- 动态体与地形分离
- 动态体与动态体分离
- 踩踏、顶推、站立等关系判定
- 箱子稳定化迭代
- 机关触发
- 玩家死亡
- 传送门/检查点/按钮触发

### 7.4 堆叠与支撑链系统

根据现有 `STACKING_SYSTEM_DOCUMENTATION.md` 和源码实现，项目已经形成明确的“堆叠/支撑”机制：

- 站在箱子上
- 站在 Replayer 上
- 箱子叠箱子
- 头顶推动上层对象
- 支撑链水平位移传递

这使得项目不仅是基础平台跳跃，还支持多层支撑和链式协同。

### 7.5 录制与回放系统

`js/record-system/` 是本游戏最核心的独特机制之一，包含：

- 录制玩家输入
- 生成 `Clip`
- 回放历史操作
- 生成 Replayer 实体
- 回放 UI 显示
- Demo1/Demo2 不同风格的录制 UI

其状态流程大致为：

- ReadyToRecord
- Recording
- ReadyToReplay
- Replaying

这个系统决定了游戏的“自己帮助自己”核心玩法，也直接支撑：

- 踩分身跳高
- 多阶段解谜
- 自我接力
- 时间差机关协作

### 7.6 Replayer 语音/气泡系统

`js/replayer-voice/` 提供了分身相关的语音气泡/提示表达能力，包括：

- `ReplayerVoice`
- `ReplayerVoiceBubble`

它是录制回放系统的人格化补充层，增强分身存在感与反馈感。

## 9. 机关系统与玩法机制

### 9.1 Demo1 机关组

`js/mechanism-system/demo1/` 主要实现以下机制：

- `ButtonPlatformLinkSystem`
  - 按钮控制平台显现、消失或可通行状态变化
- `ButtonSpikeLinkSystem`
  - 按钮控制地刺开关或危险状态变化
- `WireIndicatorSystem`
  - 机关之间的连线显示
- `WireRenderer`
  - 连线绘制

这一组机制更偏“基础机关教学”，让玩家理解按钮和目标物的因果关系。

### 9.2 Demo2 机关组

`js/mechanism-system/demo2/` 在 Demo1 的基础上扩展出更复杂的机关逻辑：

- `ButtonSpikeLinkSystem`
  - 支持更复杂的联动与表现
- `ButtonPlatformLinkSystem`
  - 延续平台联动能力
- `BtnWirePortalSystem`
  - 按钮充能连线并最终解锁 Portal

`BtnWirePortalSystem` 是 Demo2 及后续模式中非常重要的一套高级机关，其核心玩法是：

- 玩家按下按钮
- 连线开始“通电/充能”动画
- 连线头尾进度分别推进
- Portal 在完整充能后解锁
- 玩家获得通关路径

### 9.3 公告牌提示机制

`GamePageBase` 中已经封装了场景提示按钮和公告牌联动逻辑：

- 玩家与 Signboard 交互
- 发出 `SIGNBOARD_INTERACTED`
- 页面弹出可翻页的提示本体
- 离开交互范围后自动隐藏

### 9.4 房间边界切换机制

多房间关卡中，玩家到达边界后可触发：

- 左右换房
- 上下换房
- 某些房间过渡逻辑
- 某些成就或提示触发

### 9.5 检查点机制

`CheckpointSystem` 支持：

- 激活检查点
- 保存当前可恢复位置
- 关卡加载时按快照恢复
- 不同模式下控制是否允许快速返回检查点

### 9.6 传送点机制

`TeleportPointSystem` 支持：

- 关卡中的标记传送点注册
- 双向传送或配对传送
- 与房间和关卡结构共存

### 9.7 死亡与重载机制

项目内死亡相关逻辑并不是简单 `game over`，而是支持：

- 角色死亡判定
- 延迟重载请求
- 是否保留计时器快照
- 失败结果页覆盖显示
- 返回本关或返回选关

## 10. 模式与关卡体验差异

### 10.1 Demo1

定位为较早期或教学向的机关与叙事版本，核心特征包括：

- 更基础的按钮平台/地刺教学
- 明确的公告牌与提示文字引导
- 多个成就触发逻辑直接写在 Demo1 关卡中
- 录制回放机制逐步引入

### 10.2 Demo2

定位为在基础机制上强化机关设计的一组关卡，核心特征包括：

- 连线与 Portal 解锁机制
- 更复杂的按钮联动
- 不同 UI 风格的录制回放展示

### 10.3 Easy

Easy 模式的重要特征：

- 内置教程系统
- 作为主难度入口之一展示在世界选择页
- 使用计时与排行榜体系
- UI 和结算更偏正式版本流程

### 10.4 Hard

Hard 模式定位为挑战版关卡组：

- 使用同一套正式入口
- 沿用正式计时、结算和排行榜逻辑
- 关卡更偏高难度挑战

### 10.5 Special

Special 模式定位为特殊关卡集合：

- 使用独立选关入口
- 适合放特殊规则或特别设计内容

## 14. 排行榜、Firebase 与账号系统

### 14.1 技术实现方式

项目采用 Firebase 的 REST API，而不是官方 SDK。

主要原因是：

- 项目是纯前端 p5.js
- 部署在 GitHub Pages
- 不希望引入 SDK 兼容性问题

### 14.2 排行榜能力

排行榜相关能力包括：

- 每关独立榜单
- 通关提交成绩
- 本地分页拉取全部文档后排序
- 同名去重只保留最佳成绩
- 游客和账号用户命名空间分离
- 显示本次成绩、本次排名、历史最佳
- 前三名特殊视觉样式
- 当前玩家高亮

### 14.3 身份系统能力

账号与玩家身份系统包括：

- 游客昵称进入
- Firebase Auth 注册
- Firebase Auth 登录
- localStorage 持久登录态
- 账号用户名重名检测
- 游客昵称重名检测与编号追加
- 改名后同步更新排行榜历史成绩中的名字

### 14.4 数据层结构

从现有实现可看出，Firestore 中主要使用以下集合：

- `leaderboard`
- `playerNames`
- `accountNames`
- `users`

这是一个完整的“前端直连云数据库”的小型身份和成绩系统。
